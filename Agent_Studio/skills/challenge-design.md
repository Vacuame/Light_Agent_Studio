# Skill: challenge-design

用于 Challenger 子 Agent 质询 `待质询设计.md`。

## 常见执行角色

- Challenger（子 Agent）

## 权限

本 skill 不授予额外权限；执行者必须遵守当前角色文件中的权限边界。本 skill 全程只读，不写入任何文件。

## 任务输入

- 父 Agent 工作区的 `待质询设计.md`（路径由父 Agent 在创建子 Agent 时给出）
- 相关的源码、正式产物和状态文件，按需自行取证

## 流程

1. 读取 `待质询设计.md`。
2. 独立取证：不要先信设计叙述。自己读真实代码和相关文档，弄清既有系统当前如何解决同类问题、设计落点所处链路上有哪些既有机制。取证不足时，质询意见必须标注"依据不足"。
3. 按质询问题集逐项质询，每项给出质询结论和依据。
4. 汇总整体意见，按 `agents/challenger.md` 的输出格式返回父 Agent。

## 质询问题集

按深度从根本到局部：

1. 存在性：这个问题真的需要这样解决吗？有没有可能不该改这部分——改别处、少改、甚至不改？
2. 前提：设计依赖的关键前提是什么？逐个检查：经过验证吗？哪些只是假设？
3. 一致性：既有系统里同类问题是怎么解决的？本设计与既有机制是顺应还是对抗？
4. 最小性：有没有改动更小的做法？方案是在复用既有路径，还是在叠加新特例、新豁免、新机制？
5. 简洁性：方案有没有引入不必要的复杂度？

## 质询标准

- 质询意见必须带依据（文件:行 / 命令 / 文档位置），遵守 `rules/rules.md` 结论纪律。
- 可以指出更优方向（带依据），但不出完整替代方案；设计修订由父 Agent 执行、用户确认。
- 不因设计文档完整、格式工整、理由充分而放松质询；质询针对的是设计选择本身。

## 结论格式

```text
未见问题：取证后未发现该维度的问题
有疑问：依据显示设计可能不是好选择，或存在更小改动路径
设计前提可能不成立：取证结果与设计依赖的前提冲突
无法判断：缺少取证所需信息，已说明原因
```

## 禁止

- 不写入、不修改任何文件。
- 不把"没发现问题"当成"未见问题"的理由；"未见问题"必须基于实际做过的取证动作。
- 不做事实结论的证伪审查（那是 Reviewer 的职责，见 `skills/request-review.md`）。
